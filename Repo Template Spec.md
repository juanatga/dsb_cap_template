# Final Project Template — Implementation Spec

## Purpose

Create a **template repository** for a 3-month data science program's final projects. Each of the 13 students will copy this template into their own public GitHub repo and populate it with their project work. The audience for every final repo is the **general public**: someone with no data science or domain background must be able to follow the project narrative, understand the value of the work, and see how decisions were made.

The template must therefore provide **structure, not content**. Everything is scaffolding: folders, README skeleton, notebook skeletons with section headers, and instructions students replace.

Students work mostly in **Google Colab** (a few use VS Code locally). The repo must be usable from both: relative paths from the repo root, no absolute paths, no Colab-specific mounts baked into the template cells.

---

## 1. Target repo structure

```
project-template/
├── README.md
├── LICENSE                        # MIT
├── requirements.txt
├── .gitignore
├── data/
│   ├── raw/                       # original, untouched data files
│   │   └── README.md               # data provenance instructions
│   └── processed/                  # cleaned data produced by the notebooks
│       └── README.md               # "generated by notebooks — do not edit by hand"
├── notebooks/
│   ├── 01_eda.ipynb
│   └── 02_modelling.ipynb
└── docs/
    └── README.md                   # what goes here (figures, slides, extended docs)
```

Rules encoded in the structure:

- `notebooks/` is the only place notebooks live; files are prefixed `01_`, `02_` and run in that order.
- Raw data is never modified; all cleaning happens in `01_eda.ipynb`, which writes outputs to `data/processed/`.
- Large files (> ~25 MB) are never committed. The `data/README.md` explains the alternative: a download script or notebook cell that fetches the data, plus where the file lives (link, Drive, etc.).
- `.gitignore` excludes common junk: `.ipynb_checkpoints/`, `__pycache__/`, `.DS_Store`, `.env`, Colab sample-data folder (`sample_data/`).

---

## 2. README.md (root)

The root README is the **entry point for a reader who will never open the notebooks**. Skeleton with placeholder markers. Sections, in order:

1. **Title & one-line description** — `# {PROJECT TITLE}` followed by a single sentence a non-expert can understand.
2. **The problem** — 3–5 sentences: what the project is about and why anyone should care.
3. **Key result** — one headline finding/output with one supporting figure (stored in `docs/`). Placeholder until students fill it.
4. **The data** — source, size, license/terms of use, one-sentence description per dataset.
5. **How to navigate this repo** — short guide: start at this README, then `notebooks/01_eda.ipynb`, then `02_modelling.ipynb`; what lives in `data/` and `docs/`.
6. **How to reproduce** — clone, install `requirements.txt`, run notebooks in order. Include the "Open in Colab" badge pattern for each notebook.
7. **Repository structure** — the folder tree with one-line explanations.
8. **Author & credits** — student name, program, acknowledgements, data providers.
9. **License** — repo license + note if the data has a different license.

Every section header must be present in the skeleton, with short italicized instructions (`*Replace this with …*`) so students can't skip a section accidentally.

## 3. `notebooks/01_eda.ipynb` — Exploratory Data Analysis

Skeleton notebook: section headers as Markdown cells, each followed by an instruction cell describing what belongs there, and placeholder code cells where relevant. Cells contain **no real analysis**, only commented `# TODO` stubs.

Sections, in order:

1. **TL;DR** (top of notebook) — 2–3 sentences: what the data showed and what it means for the project.
2. **Introduction & motivation** — restate the problem from the README in the notebook's own words; the reader should not need to jump between files.
3. **Data provenance** — where the data comes from, how it was obtained (download/API/scrape), collection period, terms of use.
4. **Data dictionary** — a Markdown table: column name, plain-language meaning, units, expected values.
5. **Setup** — imports and path configuration (relative, from repo root).
6. **First look** — shape, sample rows, dtypes, sanity checks.
7. **Data quality audit** — missing values, duplicates, outliers, impossible values; **for each issue found, state the decision and why** (keep, fix, drop).
8. **Univariate exploration** — distributions of the key variables, one chart per question.
9. **Bivariate exploration** — relationships relevant to the project question.
10. **Key findings** — numbered list, each finding stated as: observation → what it implies for the project.
11. **Decisions carried forward** — features kept/dropped, transformations to apply, hypotheses for the modelling stage.
12. **Export** — write the cleaned dataset to `../data/processed/` (relative path) and print a confirmation line.
13. **Appendix** (optional) — secondary plots, dead ends explored.

Writing rules stated in the notebook's first cell:

- Every code cell is preceded by a Markdown cell saying, in plain language, **what** the cell does and **why**. Someone reading only the Markdown must follow the whole story.
- All cells run top-to-bottom after "Restart and run all".
- No hardcoded absolute paths (`/content/...`, `C:\Users\...`); use paths relative to the repo root with a one-time `os.chdir` or path variable documented in the Setup section.
- Charts get labeled axes and a caption sentence under each figure.

## 4. `notebooks/02_modelling.ipynb` — Modelling

Same skeleton pattern as above. Sections, in order:

1. **TL;DR** — the model's performance in one number and one sentence ("our final model predicts X with a mean absolute error of Y, Z% better than the baseline").
2. **Recap of the goal** — the problem restated, plus **the metric of success defined in plain words** and why that metric fits this problem.
3. **Setup & data loading** — loads the processed data from `../data/processed/`; if that file is missing, an explicit instruction: "run `01_eda.ipynb` first."
4. **Feature preparation** — transformations and their justification (carry-over from the EDA decisions).
5. **Train/test split** — the split performed with a one-paragraph plain-language explanation of why held-out evaluation matters (analogy welcome: grading with questions the student never saw).
6. **Baseline model** — a deliberately simple model (class mean, majority class). Explicitly framed as "the bar to beat."
7. **Candidate models** — one model at a time; each preceded by a Markdown cell answering "why this model for this problem?"
8. **Evaluation & comparison** — the chosen metric(s) computed for baseline and candidates, plus at least one visual (confusion matrix, residuals, predicted vs. actual). Includes a comparison table of results.
9. **Error analysis** — where the model fails and what patterns the failures reveal.
10. **Interpretation** — feature importance or equivalent (permutation importance is fine), translated into plain language.
11. **Limitations & ethics** — what the model can't do, biases in the data, caveats for real-world use.
12. **Conclusion & next steps** — honest summary including what did not work.

Same writing rules as notebook 01 (plain-language Markdown before every code cell, top-to-bottom execution, labeled charts, relative paths).

## 5. Supporting files

- **`requirements.txt`** — a starter with `pandas`, `numpy`, `matplotlib`, `scikit-learn`, `jupyter`, each unpinned with a comment `# pin the versions you actually used (pip freeze) before submitting`. Note: Colab users should still fill this in; the file records the environment for the public reader.
- **`LICENSE`** — MIT, with the program/organization as the copyright line and `{YEAR}` `{AUTHOR}` placeholders.
- **`.gitignore`** — `.ipynb_checkpoints/`, `__pycache__/`, `.DS_Store`, `sample_data/`, `.env`, `*.pyc`.
- **`data/raw/README.md`** — instructions: what goes in this folder (untouched originals), how to document source/date/license of each file, what to do if the file is too large for GitHub (download script or link + fetch cell).
- **`data/processed/README.md`** — "Files here are generated by `notebooks/01_eda.ipynb`. Do not edit by hand; re-run the EDA notebook instead." Plus a mini data dictionary for the processed output.
- **`docs/README.md`** — final report figures, presentation slides, any extended explanation go here; one line per item once added.

## 6. Implementation notes for the code agent

- Build this as a plain local directory that will become a git repo; no git initialization commands needed in the code itself (user handles `git init` locally), but include them in a short `SETUP.md` or at the bottom of the root README as an appendix for students: `git init`, `git add .`, `git commit`, creating a GitHub repo, pushing. Include both the GitHub-web path and the command-line path.
- Notebooks must be **valid `.ipynb` JSON** with proper `nbformat` structure: Markdown cells containing the section headers and instructions, empty code cells containing only `# TODO` comments. Verify the JSON parses.
- Section headers in notebooks use Markdown `## N. Title` numbering matching the lists above, so the numbering doubles as a checklist.
- Instructions inside the skeleton are addressed to the student ("Replace this with…"), written in simple, friendly language, with analogies for beginners — the program's students do not have a formal CS or statistics background.
- Keep everything **framework-agnostic and domain-agnostic**: no project-specific content, no example analysis that a student could mistake for required content. Placeholders use `{curly braces}` for values and italic instructions for free-text sections.
- Include at the top of each notebook's first cell a one-line note: "Delete instruction cells when populating the notebook" — so instructions don't survive into the final repo.

## 7. Review checklist (used by the instructor when reviewing each migrated repo)

Check per repo, after students populate the template:

**Structure**
- [ ] Folders and files match the target layout; no notebooks outside `notebooks/`; raw and processed data separated correctly.
- [ ] LICENSE, `requirements.txt` (pinned), `.gitignore` present and filled.
- [ ] No data files > 25 MB committed; oversized files handled via fetch script/link instead.

**README**
- [ ] All nine sections present, no placeholder text remaining.
- [ ] Key result states one concrete number/finding.
- [ ] Reproduction instructions actually work (fresh clone, fresh Colab session from the repo).

**Notebooks**
- [ ] Every code cell preceded by a plain-language Markdown cell.
- [ ] Running order is 01 then 02; 02 loads data only from `data/processed/`.
- [ ] Both notebooks pass "Restart and run all" end to end.
- [ ] Data dictionary exists; decisions for each data-quality issue documented.
- [ ] Baseline model present and reported alongside the final model.
- [ ] Limitations/ethics section present and substantive (not a placeholder).
- [ ] No leftover template instruction cells; no leftover `TODO` comments.

**Reader test (the most important one)**
- [ ] A person with no data science background can read the root README alone and explain: what the project did, what the result was, and why the decisions were reasonable.

**Git / process (lightweight — no peer pairing)**
- [ ] Work happened on a `tidy_work` branch created from the template.
- [ ] Merge to `main` via pull request opened by the instructor, student's own commits only.
- [ ] `main` runs after merge; the working branch ran before merge.
